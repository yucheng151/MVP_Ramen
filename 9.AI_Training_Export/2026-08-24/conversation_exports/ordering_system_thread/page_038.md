### 1. 為什麼需要公開訂單服務

手機前台在公開網路，HMI 電腦則通常在店內區域網路。如果直接讓手機連 HMI，需要公開 HMI 的網路入口，安全性與交接都不好。

建議：

- 手機訂單先存在公開訂單服務。
- HMI 主動向外取得訂單，不開放外部直接連入 HMI。
- PLC 完全不連網路，只接受 HMI 指令。
- 公開服務與網域由公司帳戶持有。

HMI 在操作人員眼中仍然是後台；公開訂單服務只是負責在手機與 HMI 之間傳遞資料。

### 2. 資料設計

一張訂單與每碗任務必須分開。

```text
訂單 A023，共 3 碗
├─ A023-01：等待製作
├─ A023-02：等待製作
└─ A023-03：等待製作
```

主要資料如下。

#### 訂單 Orders

```text
order_id
pickup_number
pickup_name
total_bowls
completed_bowls
total_price
status
customer_token
created_at
```

#### 單碗任務 BowlJobs

```text
bowl_id
order_id
sequence
product
noodle_firmness
status
selected_noodle_slot
started_at
completed_at
error_code
retry_count
```

#### 麵櫃 NoodleSlots

```text
slot_id：1～10
quantity
reserved_quantity
enabled
updated_at
```

#### 空盒格 EmptyBins

```text
bin_id：1～2
current_quantity
capacity
enabled
```

### 3. 狀態規劃

訂單狀態：

```text
已建立 → 等待製作 → 製作中 → 可取餐
                         └→ 異常
```

單碗狀態：

```text
等待派工
→ 準備派工
→ PLC 已接受
→ 製作中
→ 完成

任何階段都可能進入異常
```

機台狀態：

```text
離線
待機
製作中
異常
```

整張訂單只有在所有 `BowlJobs` 都完成後，才變成「可取餐」。

### 4. HMI 派工邏輯

目前容量固定為：

```text
machine_capacity = 1
```

HMI 反覆執行：

```text
1. 確認 PLC 已連線。
2. 確認自動模式且無警報。
3. 確認目前沒有正在製作的任務。
4. 取得最早一筆等待中的單碗任務。
5. 選擇有庫存的麵格。
6. 寫入該碗需要的參數。
7. 發出一次自動啟動。
8. 確認 Main_step 已離開 0，代表 PLC 接受並開始執行。
9. 等待 PLC 跑完單碗流程。
10. 確認 Main_step 從非 0 回到 0，且沒有異常。
11. 將該碗標記完成。
12. 處理下一碗。
```

不能只看到 `D1400 = 0` 就認定完成，因為尚未啟動時也是 0。必須確認完整變化：

```text
0 → 10～90 → 0
```

### 5. PLC 的責任

PLC 保持目前的單碗自動流程，不必知道顧客總共點幾碗：

```text
收到一次啟動
→ 執行 Main_step 10～90
→ 完成一碗
→ 回到 Main_step 0
```

HMI 不控制每一個汽缸、Robot、煮麵時間或輸送帶步驟，只讀取 PLC 狀態並決定是否派下一碗。

### 6. 庫存扣除時機

建議分為「預留」與「實際扣除」：

```text
顧客訂單成立：reserved_quantity +1
PLC 確認開始該碗：實際庫存 -1、預留 -1
製作前取消：預留 -1
啟動失敗：不扣實際庫存
```

可販售數量：

```text
10 個麵格總數
− 已預留但尚未製作的碗數
```

空盒容量也要預留，避免接受訂單後才發現兩個空盒格都滿了。

### 7. 顧客完成通知

手機訂單頁透過公開服務查詢狀態：

```text
HMI 確認一碗完成
→ 上傳 completed_bowls
→ 手機顯示「已完成 2／3 碗」

全部完成
→ 訂單改為可取餐
→ 手機播放聲音、震動並顯示取餐通知
```

第一版要求顧客保留訂單頁面；後續再增加瀏覽器推播。

### 8. 異常與重新啟動

這部分第一次就要寫好，否則正式使用容易重複啟動：

- HMI 程式重啟後，先讀取 `D1400`，不能直接重送上一碗。
- 若 PLC 還在 Step 10～90，HMI 恢復監看原任務。
- PLC 異常時暫停整條派工佇列。
- 操作人員選擇重試、取消或人工完成。
- 每次啟動都保存唯一指令編號，避免網路重送造成重複訂單。
- 訂單和任務使用 SQLite／正式資料庫保存，不能只放在記憶體。

### 9. 預留未來擴充

資料庫從一開始就用單碗任務設計，但目前容量為 1。未來 PLC 支援三碗時，只改：

```text
machine_capacity = 3
PLC 派工介面
PLC 回報的可用容量
```

手機前台、訂單資料及顧客通知都不需要重寫。

### 10. 開工前必須確認的 PLC 介面

目前還需要確定：

- 自動啟動的 PLC 位址或握手指令。
- 自動流程接受啟動的確認方式。
- `D1400` 回到 0 是否正式代表一碗完成。
- 異常狀態與錯誤碼位址。
- Step 10 的 `IPC Command 103` 由誰執行。
- 麵格編號與麵條參數要寫入哪些位址。

只要先把這份「HMI ↔ PLC 單碗介面」固定，其他後台功能就能一次按上述架構完成。

### 製作批次

例如目前等待佇列有四碗：

```text

├─ Slot 1：A023-01
├─ Slot 2：A023-02
└─ Slot 3：A023-03

等待下一批：
└─ A023-04
```

HMI 寫給 PLC：

```text

slot_1.noodle_slot
slot_1.cook_time

slot_3...
```

```text

```

```text
max_batch_size = 3
bowl_count = 1、2 或 3
```

因此 HMI、訂單及資料庫不需要重寫。

### PLC 內部三個煮麵位

每個煮麵位都需要獨立狀態：

```text
空閒
→ 等待下麵
→ 煮麵中
→ 煮好升起
→ 等待輸送帶
→ 已放行
→ 完成
```

PLC 內部可以表示為：

```text
CookerSlot[1]
CookerSlot[2]
CookerSlot[3]
```

每格保存：

```text
bowl_id
recipe
cook_time
elapsed_time
status
lifted_wait_time
error_code
```

### 單線輸送帶互鎖

三碗可以同時煮，但只能逐碗使用輸送帶：

```text
煮麵位 1 ─┐
煮麵位 2 ─┼→ 等待輸送佇列 → 輸送帶 → 後續流程
煮麵位 3 ─┘
```

PLC 控制規則：

1. 煮好後立即升起，不繼續泡在水裡。
2. 將該煮麵位加入等待輸送佇列。
3. 輸送帶空閒時，只允許一個煮麵位放行。
4. 確認該碗離開後，輸送帶才接受下一碗。
5. 升起等待超過品質時間時產生警示。
6. 任一碗異常時，不應讓其他碗與訂單編號錯配。

### PLC 回報不能只有整批完成

PLC 應逐碗回報：

```text
batch_id
slot_id
bowl_id
slot_status
completed_bowl_id
completed_count
batch_status
error_code
```

例如：

```text
B001：
Slot 1 完成
Slot 2 等待輸送帶
Slot 3 煮麵中
完成數量 1／3
```

HMI 收到單碗完成訊號後，就更新對應的 `BowlJob`，不能等整批三碗全部完成才更新。

### HMI 組批規則

```text
本批碗數 =
min（等待中的單碗任務數、PLC 可接受容量、可用麵盒數、空盒剩餘容量）
```

例如：

```text
等待 5 碗
PLC 最大容量 3
庫存足夠
空盒空間足夠

本批送 3 碗，剩餘 2 碗等待下一批
```

不同顧客的訂單也可以放在同一批，但每碗必須保留自己的 `bowl_id`，避免通知錯人。

### 最終架構

```text
手機訂單
→ Orders
→ 拆成 BowlJobs
→ HMI 組成 Batch（1～3 碗）
→ PLC 分配三個 CookerSlot
→ 煮好後分別升起等待
→ PLC 逐碗取得輸送帶
→ PLC 逐碗回報完成
→ HMI 更新各訂單進度
→ 同張訂單全部完成後通知顧客
```

關鍵是從一開始就把介面寫成「批次最多三碗」，但目前設定 `max_batch_size = 1`。等三碗 PLC 流程完成後，只把容量改成 3，前台與後台架構都可以沿用。
